Abstract

This document serves as the Software Requirements Specification (SRS) for the Local Greetings web application. Local Greetings is a community-oriented sports platform that allows residents of Iași, Romania, to discover, organize, and participate in local sports activities and meetups. The platform connects athletes, casual players, and venues, providing an interactive map, advanced search filters, and moderation controls.

Unlike traditional social networks, Local Greetings focuses on real-time neighborhood coordination, utilizing an interactive map powered by OpenStreetMap and Leaflet.js, and a robust server-side architecture built with vanilla PHP 8.x, ensuring cross-platform speed and a low resource footprint. The specification described herein follows the structural guidelines of W3C Scholarly HTML for academic document representation and the functional definitions of the IEEE 830-1998 standards for software requirements.

1. Introduction

1.1 Purpose

The purpose of this document is to define the software requirements for the Local Greetings web platform, version 1.0. This specification describes both functional and non-functional requirements, detailed use cases, architecture design, database schemas, and external interface descriptions to guide developers, testers, and evaluators.

The document covers the full scope of the platform, including user authentication, security, location subscriptions, event generation, search filters, geolocation mapping, and administrative moderation. It is intended to serve as a single source of truth for both technical grading and future system maintenance.

1.4 Product Scope

Local Greetings is a specialized web application built with a PHP backend and a pure HTML5/CSS3/JavaScript frontend. It aims to solve the problem of finding partners for team sports (like football, basketball, and tennis) and discovering available playing venues in the city of Iași. It does this by offering an interactive map powered by Leaflet, email verification, customizable user profiles, dynamic event creation, and an admin dashboard for moderation.

The system acts as a real-time event generator, enabling users to:

  • Organize matches, coordinate venues, and join local groups.
  • Subscribe to specific locations to receive email digests whenever a new match is scheduled at that court.
  • Limit login brute-force attempts and verify email authenticity before engaging in the community.

2. Overall Description

2.1 Product Perspective

Local Greetings is a self-contained, lightweight web application. It operates under a classic client-server model, where the frontend communicates with the server via structured RESTful JSON APIs. The backend utilizes PHP 8.x for routing and data modeling (using custom Models and Controllers), and MySQL for persistence.

The client frontend consists of static HTML, CSS, and JS files served by the web server. Since there is no heavy framework overhead (such as Node compilation), the client remains fast and consumes minimal memory. All database actions, logic checking, and email rendering are delegated to the server.

Architecture Note: The platform is completely decoupled. Frontend pages are static HTML/JS files which perform asynchronous fetch requests to the PHP endpoints under backend/public/.

2.2 Product Functions

The primary functions of the Local Greetings platform include:

  • User Account Management: Registration, email verification, login attempt limits (brute-force protection), token-based persistent sessions, and password recovery.
  • Event Creation & Management: Organizers can create events specifying start/end date, maximum participants, skill levels (Beginner, Medium, Expert), sport type, and specific venues.
  • Interactive Map: Visualizes sports venues in Iași using coordinate markers with popups containing venue information and active events.
  • Search and Filter Engine: Enables users to search events by keywords, filter by sport type, venue, date, or skill levels.
  • Profile and Statistics: Visualizes user-specific game metrics, favorite sports, favorite zones, and active event subscriptions.
  • Administrative Controls: Allows administrators to ban inappropriate users and delete events that violate community guidelines.

2.3 User Classes and Characteristics

  1. Unauthenticated Guests: Can view the home page, read the latest events list, and browse venues on the search map. Cannot join or create events.
  2. Registered Athletes: Verified users who can create events, join existing events, comment on event pages, subscribe to locations, and customize their profiles.
  3. Administrators: Users with elevated privileges (role = 'admin') who access the Admin Panel to ban users, delete events, and audit access tokens.

2.4 Operating Environment

  • Client-Side: Modern web browsers (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+) on Desktop and Mobile.
  • Server-Side: Apache/Nginx web server with PHP 8.0+ and MySQL 5.7+ (local deployment using XAMPP/WAMP is fully supported).

2.5 Design and Implementation Constraints

The frontend is written in vanilla HTML5, CSS3, and JavaScript to keep the page load footprint minimal. No heavy frontend frameworks (like React, Angular, or Vue) are used. On the backend, routing and database interactions are written in raw PHP (conforming to PSR standards for autoloading and MVC partitioning) to ensure simple deployment on standard web hosting packages.

Additionally, database access must strictly route through PDO prepared statements, and session data is restricted to bearer tokens to maintain database-level authentication, making the API stateless.

JavaScript OOP Constraint: As the frontend script handles lightweight DOM manipulations and event dispatching, it does not warrant complex Object-Oriented JS structures. Instead, it relies on procedural and functional event bindings (such as event listeners on specific forms).

Fara WebSockets (WebSocket Exclusion): Real-time syncing is managed purely via HTTP polling/REST AJAX calls instead of WebSockets. This avoids the overhead of managing concurrent socket threads and persistent TCP connections, making the server stateless and highly reliable. If an update occurs, the browser makes a new fetch request to asynchronously reload the modified elements.

2.6 User Documentation

An interactive install guide is provided in the project repository root (README.md and admin-install-guide.md), detailing XAMPP setup, database initialization, and local SMTP log configurations.

2.7 Assumptions and Dependencies

  • It is assumed that the client machine has an active internet connection to load external resources like Google Fonts and Leaflet tile assets.
  • Database connection relies on MySQL running on port 3306 with credentials matching backend/db_connection.php.
  • It is assumed that the server environment supports standard PHP timezone configurations to properly evaluate event date ranges.

3. External Interface Requirements

3.1 User Interfaces

The user interface is designed with a premium, responsive layout. It features a sticky navigation bar with glassmorphism, vibrant badges indicating sports, and a clean card grid for event listings. Headings use the Google Font Outfit, and body text uses Inter. The UI is designed to scale dynamically from mobile devices (min 320px) to large screens (up to 1920px).

Key screens include:

  • Homepage (index.html): Features a prominent featured event card, a grid showing upcoming activities, and the event creation form.
  • Map Finder (search.html): A split-pane layout displaying the interactive map on the left and a list of matching venue cards on the right.
  • Profile Area (profile.html): Displays activity metrics (number of games joined, hosted, usual zones) using responsive CSS bars.

3.2 Hardware Interfaces

There are no special hardware interfaces. The application uses standard pointer input (mouse, trackpad) and touch screen gestures on mobile devices, alongside keyboard accessibility controls.

3.3 Software Interfaces

The platform interfaces with a MySQL database via the PHP PDO driver. The map page embeds Leaflet JS which communicates with the OpenStreetMap API to pull map tile assets. Mail generation interfaces with a local mail log (backend/storage/mail.log) or standard external SMTP servers (like Gmail SMTP).

3.4 Communications Interfaces

All network communication between client and server is done via HTTPS using asynchronous HTTP requests (AJAX/Fetch API). API payloads are structured strictly in application/json. Sessions are managed using custom token hashes sent in the Authorization: Bearer <token> header.

Authorization Header Handling: The client JavaScript injects the token explicitly using standard Fetch request headers:

This avoids relying on automatic server variables which are frequently stripped by Apache modular configurations. On the backend, `Request::bearerToken()` checks both `HTTP_AUTHORIZATION` and fallback headers like `X-Auth-Token` to ensure complete cross-server compatibility.

4. System Features

4.1 Authentication & Account Protection

Description

Allows users to securely register, verify their email address, login, and reset their password.

Server-Side Credential Verification

When registering or logging in, the server performs extensive validation on the credentials:

  • Email: Validated against RFC 5322 specifications using PHP's filter_var($email, FILTER_VALIDATE_EMAIL) and converted to lowercase to prevent duplicates.
  • Password: Register requires a minimum length of 8 characters and must contain at least one letter and one number. In database storage, passwords are hashed using `password_hash($password, PASSWORD_DEFAULT)` which implements secure `bcrypt` rounds.

Stimulus/Response Sequence

Lockout logic: If a user fails to login 5 times consecutively, their account email is locked for 10 minutes (stored in the login_attempts table), preventing brute-force attacks.
  • Stimulus: User enters email and password on the login screen.
  • Response: Server checks login_attempts. If not locked, it fetches the user from the database, verifies the password hash, updates attempt counters, generates an auth token, and returns it to the client.

4.2 Event Management

Description

Registered users can schedule sports events.

Event Overlap Check (Validation)

To prevent double-booking of sports courts and venues, the event creation engine validates that the target venue does not have any active events scheduled within 2 hours of the requested start time.

If the count exceeds 0, the server rejects the request with a `422 Unprocessable Entity` status code and return a clear validation error to the client, preventing double-scheduling.

4.3 Search Engine & Interactive Venue Map

Description

Browsing and filtering events.

Functionality

The map visualizes different zones in Iași (e.g. Copou, Tătărași, Nicolina). Clicking on a location pin reveals active meetups scheduled there. Users can use filter chips to refine listings by sport type, date, or skill level.

RSS Feed Reader Integration

The platform generates an XML RSS 2.0 feed at backend/public/rss.php containing all upcoming sports events. This allows external aggregators and calendars to subscribe to city sports activities.

4.4 Admin Dashboard

Description

Central administration page (admin.html) accessible only to users with the role = 'admin' flag.

Moderation Actions

5. Other Nonfunctional Requirements

5.1 Performance Requirements

  • API responses from the backend should resolve within 200ms under standard loads.
  • Static assets (HTML, CSS, images) should be optimized to score 90+ on Lighthouse performance audits.
  • The Leaflet map page should lazy-load markers based on visible map bounds to minimize DOM overhead on mobile devices.

5.2 Safety Requirements

The system employs soft deletes for major records, and email links have short validation windows (1 hour for verification and password resets) to prevent unauthorized hijackings.

5.3 Security Requirements

  • Password Security: Passwords must be hashed using the secure bcrypt algorithm (via PHP's password_hash).
  • SQL Injection: All database queries use prepared statements with parameter binding via PDO (no raw queries with variable interpolation are allowed).
  • Cross-Site Scripting (XSS): Input data rendered in the DOM is sanitized using text node parsing or escaping helpers. The application strictly forbids using innerHTML in client-side scripts to prevent script execution vulnerabilities.
  • Cross-Site Request Forgery (CSRF): Critical POST operations require valid CSRF tokens verified on the backend.

Stateless CSRF Protection

To prevent cross-site request forgery without session state overhead, the backend signs CSRF tokens using HMAC-SHA256:

This token contains a timestamp. When checking validity, the server decodes the token, verifies that it hasn't expired (TTL of 2 hours), recomputes the signature using `hash_equals` (timing attack safe comparison), ensuring absolute stateless safety.

5.4 Software Quality Attributes

The project relies on decoupled components, separating business logic into specific Controllers (e.g., UserController.php, EventController.php) and models mapping database interactions. This ensures high maintainability and extensibility.

5.5 Business Rules

Users must verify their email addresses prior to gaining event creation and comment posting privileges. Banned users are immediately logged out, their active auth tokens are revoked, and their credentials block subsequent login attempts.

6.1 Database Schema Details

The database structure uses foreign key constraints to maintain referential integrity. User profiles and auth tokens are cascade deleted if the main user record is removed.

6.2 Autoloading & MVC Design

The project maps classes under the App\ namespace to files inside the backend/src/ folder. Autoloading is registered in backend/autoload.php. Controllers intercept frontend requests and return structured JSON responses via App\Support\Response::json().

Request endpoints are clean and separate:

  • backend/public/login.php maps to UserController::login()
  • backend/public/events.php maps to EventController::index()
  • backend/public/admin/ directory handles restricted administrative endpoints.

6.3 Securing Data

Token storage does not use standard cookies. Tokens are saved in the client's localStorage and transmitted using the Authorization: Bearer <token> header. This ensures protection against standard CSRF vectors on session cookies, since scripts from other domains cannot access localStorage properties.

Appendix A: Glossary

Auth Token
A secure hash sent from client to server to validate user identity without using cookies or PHP sessions.
Leaflet JS
An open-source JavaScript library used for building interactive maps.
CSRF
Cross-Site Request Forgery, an attack vector where unauthorized commands are executed from a trusted user.
XAMPP
An easy-to-install Apache distribution containing MariaDB (MySQL), PHP, and Perl.
HMAC
Hash-based Message Authentication Code, a cryptographic construction used to verify message integrity and authenticity.
